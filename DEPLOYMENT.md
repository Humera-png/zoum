# Deployment checklist

Two independent deployables:

1. **Frontend** — static `dist/` build → Hostinger Premium (`public_html`)
2. **Contact API** — Cloudflare Worker (`worker/`) → Cloudflare's edge

Neither needs the other to build. The frontend just needs the Worker's URL
once it exists.

---

## Environment variables — complete reference

| Variable | Lives in | Public or secret | What it is | Where to get it |
|---|---|---|---|---|
| `VITE_CONTACT_API_URL` | Frontend `.env` | **Public** — bundled into client JS, visible to anyone via view-source | The deployed Worker's URL, e.g. `https://zoum-contact-api.<subdomain>.workers.dev` | Printed by `wrangler deploy` after you deploy the Worker (step 4 below) |
| `RESEND_API_KEY` | Worker **secret** (`wrangler secret put`) + `worker/.dev.vars` for local dev | **Secret** — never in frontend, never in `wrangler.jsonc`, never committed | Authenticates the Worker to Resend's API to send email | [resend.com/api-keys](https://resend.com/api-keys) — create a free Resend account, generate a key |
| `ALLOWED_ORIGINS` | `worker/wrangler.jsonc` → `vars` (committed) | Public — not sensitive, just a config list | Comma-separated allow-list for CORS; the Worker rejects any request from an origin not on this list | You set it — already prefilled with the production domain (www + non-www) and localhost dev ports |
| `CONTACT_TO_EMAIL` | `worker/wrangler.jsonc` → `vars` (committed) | Public | Where inquiry emails get delivered | You set it — already prefilled as `contact@zoumconsultancy.com` |
| `CONTACT_FROM_EMAIL` | `worker/wrangler.jsonc` → `vars` (committed) | Public | The Resend-verified "From" address inquiry emails are sent as | You set it — **must be on a domain you've verified in Resend** (see step 2) |
| `RATE_LIMIT_KV` (binding, not a var) | `worker/wrangler.jsonc` → `kv_namespaces` (committed, holds an *id*, not a secret) | Public — a resource id, not sensitive | Workers KV namespace backing the per-IP rate limiter | Generated by Cloudflare when you run `wrangler kv namespace create` (step 3) |

**No database is used.** Leads are relayed by email via Resend only — this
was an explicit scope decision (see `plans/partitioned-dreaming-seahorse.md`
in the earlier session), not an oversight. There is no `DATABASE_URL`
anywhere in this project.

**Verified no secrets leak into the frontend bundle**: `grep -r "resend\|re_[A-Za-z0-9]" dist/`
after a production build returns nothing. Vite only inlines vars prefixed
`VITE_`; `RESEND_API_KEY` has no such prefix and lives exclusively in the
Worker's secret store, which the frontend build never touches.

## Step 1 — Resend account

1. Sign up at [resend.com](https://resend.com) (free tier is enough for a contact form).
2. **Domains → Add Domain** → enter `zoumconsultancy.com` → add the SPF/DKIM
   DNS records it gives you at your domain registrar. Wait for it to show
   **Verified** (usually minutes, can take longer depending on DNS propagation).
   *Until this is verified, Resend will reject sends from `@zoumconsultancy.com`
   — you can only send from their sandbox `onboarding@resend.dev` address.*
3. **API Keys → Create API Key** → copy it (starts with `re_`). You won't be
   able to see it again after this screen.

## Step 2 — Worker: local setup

```bash
cd worker
npm install
cp .dev.vars.example .dev.vars
# paste your real re_... key into .dev.vars
```

## Step 3 — Worker: KV namespace (rate limiting)

```bash
npx wrangler kv namespace create RATE_LIMIT_KV
npx wrangler kv namespace create RATE_LIMIT_KV --preview
```

Each command prints an id. Paste them into `worker/wrangler.jsonc`:

```jsonc
"kv_namespaces": [
  { "binding": "RATE_LIMIT_KV", "id": "<paste first id>", "preview_id": "<paste second id>" }
]
```

## Step 4 — Worker: deploy

```bash
npx wrangler login          # first time only, opens a browser to authorize
npx wrangler secret put RESEND_API_KEY   # paste your re_... key when prompted
npm run deploy
```

Copy the URL Wrangler prints (`https://zoum-contact-api.<subdomain>.workers.dev`).

**Test it's alive:**
```bash
curl -X POST https://zoum-contact-api.<subdomain>.workers.dev \
  -H "Origin: https://zoumconsultancy.com" \
  -F name="Test" -F email="you@example.com" -F company="Test Co" \
  -F reason="general" -F message="Deployment smoke test" -F website=""
# expect: {"ok":true}
```

## Step 5 — Frontend: point at the deployed Worker

In the project root:
```bash
echo "VITE_CONTACT_API_URL=https://zoum-contact-api.<subdomain>.workers.dev" > .env
```

## Step 6 — Frontend: build

```bash
npm run build
```

This runs `vite build` then the prerender script — it will **fail loudly**
(non-zero exit) if any route doesn't render completely, so a successful run
means the output is good. Confirm:
```bash
ls dist/            # index.html, assets/, sitemap.xml, robots.txt, .htaccess
```

## Step 7 — Upload to Hostinger

Upload the **contents** of `dist/` (not the `dist` folder itself) into
`public_html/` via Hostinger's File Manager or FTP/SFTP. The included
`.htaccess` handles routing — no server config needed on Hostinger's end.

## Step 8 — Verify in production

- Visit the live site, submit the contact form for real, confirm the email
  arrives with the correct Reply-To.
- `curl -I https://zoumconsultancy.com/robots.txt` and `/sitemap.xml` — both 200.
- View-source (not devtools) on a couple of pages — confirm `<title>`,
  meta description, and JSON-LD are present in the raw HTML.

---

## If you ever redeploy the Worker to a new URL

Update `VITE_CONTACT_API_URL` in `.env`, rebuild (`npm run build`), and
re-upload `dist/`. That's the only frontend change ever needed for a Worker
redeploy.
