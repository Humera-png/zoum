1

What is automation?

Definition: automation is getting a computer to do, on its own, something a person currently does by hand — the same way, every time, without needing to be asked.

Analogy: think of a bank's ATM. Before ATMs, a person had to walk into a branch and hand cash to a teller. The ATM automated that: it does the exact same job, every time, without a human doing it manually. Software automation is the same idea, applied to digital tasks — sending an email, updating a spreadsheet, replying to a customer.

The one test for "is this worth automating": two questions — is it repetitive (happens more than once), and is it stable (it happens roughly the same way each time)? If both are yes, it's a good automation candidate. If a task is different every single time, automating it is usually more work than it saves.

2

What is n8n?

Definition: n8n (pronounced "n-eight-n," short for "nodemation") is a visual workflow automation tool. Instead of writing a computer program line by line, you build an automation by placing boxes — called nodes — on a canvas and connecting them with lines, in the order you want things to happen.

Analogy: imagine a flowchart on a whiteboard — a box for "form submitted," an arrow to a box for "check the data," an arrow to a box for "send an email." n8n is that flowchart, except each box is a real, working piece of software, and the whole diagram actually runs.

Why this matters for people with no coding background: the visual, box-and-line approach means you don't need to know a programming language to build something that would otherwise require writing real code. You still think logically and precisely — you're just doing it with boxes instead of text.

Why n8n specifically (compared to tools like Zapier or Make): it can be self-hosted (no dependence on one company's servers), it doesn't charge per individual automation run the way some competitors do, and — the reason it's taught in this class — it has first-class support for calling AI models directly inside a workflow.

3

The canvas & the workflow

What is a workflow? A workflow is one complete automation — one flowchart, made of nodes connected in order, that does one job from start to finish. Everything you build in n8n lives inside a workflow.

What is the canvas? The canvas is the open, blank space where you build a workflow — literally the whiteboard the nodes get placed on. You add nodes to it, drag them around, and draw connections between them by dragging from one node's edge to the next node.

Reading a workflow left to right: by convention, n8n workflows run left to right (or top to bottom) — the leftmost node runs first, and execution flows along the connecting lines to whatever's next.

4

What is a node?

Definition: a node is one single step in a workflow. Each node does exactly one job — fetch some data, transform it, send an email, ask an AI model a question, and so on. You build complex automations by chaining many simple nodes together, not by making one node do everything.

Analogy: think of a factory assembly line. Each station on the line does one small job — attach a wheel, tighten a bolt, spray paint — and the product moves down the line from station to station. A node is one station. A workflow is the whole line.

Every node has: settings on the left/inside (what should this node do, specifically — e.g. which URL to call, what text to send), and, after it runs, an output panel showing exactly what data it produced. Click any node to see both.

5

Trigger nodes vs. regular nodes

Every workflow needs exactly one starting point — a trigger node. A trigger is a special kind of node whose only job is to decide when the workflow should run. Every other node in the workflow is a "regular" node (sometimes called an "action" node) — it does something with the data, but it doesn't decide when the workflow starts.

The rule to teach: "The very first node in any workflow is always a trigger. Everything after it is a regular node." n8n enforces this — you cannot run a workflow that doesn't start with a trigger.

There are three trigger types used constantly in this course, covered in full next: Manual, Webhook, and Schedule.

6

Manual Trigger

What it is: the simplest possible trigger. It does nothing on its own — it fires only when a person clicks the "Test workflow" button inside n8n.

What it's for: building and testing. While you're constructing a workflow, you don't want to wait for a real webhook or a scheduled time to see if it works — you want to run it right now, on demand, and see the result immediately. That's exactly what Manual Trigger is for.

What it's not for: a Manual Trigger workflow will never run by itself once you close n8n — a person always has to click the button. It's a development tool, not something used in a finished, "live" automation.

7

Webhook Trigger — full explanation

What is a webhook, in plain English? A webhook is a way for one piece of software to instantly notify another piece of software the moment something happens — without either one having to constantly check in with the other.

Analogy — a doorbell, not a delivery you have to watch for: imagine you're expecting a package. Without a doorbell, you'd have to keep walking to the window every few minutes to check if it's arrived — that's "polling," constantly checking. A doorbell means the delivery person notifies YOU the instant they arrive — you don't have to check at all. A webhook is the doorbell. Instead of your workflow constantly asking "has anything happened yet?", the other system rings the doorbell (sends a request) the instant something happens.

How it actually works, step by step:

  1. You add a Webhook node to a workflow in n8n.
  2. n8n generates a unique web address (a URL) just for that node — something like https://your-n8n.com/webhook/abc123.
  3. You give that URL to whatever system needs to notify you — for example, you paste it into a website's form-builder settings, or into another app's "notify this URL when X happens" field.
  4. When the event actually happens elsewhere (someone submits the form), that other system sends an HTTP request to your webhook's URL, carrying the relevant data along with it (the person's name, email, message, etc.).
  5. n8n receives that request instantly, and your workflow starts running immediately — with that incoming data available to every node after it.

What is an "HTTP request," for someone hearing the term for the first time? Every time a browser loads a web page, it's making an HTTP request to a server and getting a response back. A webhook works the same way, except instead of a browser asking for a page, another piece of software is sending data to your workflow's URL.

HTTP Method — GET vs. POST (teach this briefly, it comes up immediately): a GET request generally just asks for information; a POST request sends data along with the request. A form submission (a lead's name, email, message) is always sent as a POST, because it's delivering data, not just asking a question. This is why the Webhook node in this class is always set to POST.

Test URL vs. Production URL — the distinction that trips people up: every Webhook node actually gives you two different web addresses:

URLWhen it worksUsed for
Test URLOnly while you've clicked "Listen for test event" inside n8n and are actively watchingBuilding and testing, while you're in the editor
Production URLWorks continuously, any time, once the workflow is toggled ActiveThe real, live automation, running unattended

Say this explicitly: "While we're building today, we always use the Test URL, because we're sitting here watching it happen. The Production URL is what you'd give to a real website form once the automation is finished and turned on."

Common mistake: sending a test request without first clicking "Listen for test event" — the webhook isn't listening yet, so nothing happens and the node stays grey. Always click Listen first, then send the request.

If asked: "Is a webhook the same as an API?"

Related, but not identical: "An API is a general way for two systems to talk to each other — it can involve you asking a question and getting an answer back. A webhook is specifically the reverse direction: the other system reaches out to YOU, the moment something happens, without you asking first."

Real-world example to give the room: "Imagine a 'Contact us' form on a company website. When a visitor clicks Submit, the website doesn't just save the message quietly — it can be configured to immediately send that data to a webhook URL. The moment they hit Submit, your n8n workflow wakes up with their name, email, and message already in hand. No one had to check an inbox or refresh a spreadsheet."

8

Schedule Trigger — full explanation

What is it? A Schedule Trigger fires a workflow automatically at set times — not because something happened elsewhere, but because a certain amount of time has passed, or a clock has hit a specific time.

Analogy — an alarm clock, not a doorbell: where a Webhook is a doorbell (reacts to an event), a Schedule Trigger is an alarm clock — it doesn't wait for anything to happen, it just goes off at the time you set, every time, on its own.

How it works: you configure the trigger with how often it should run — for example, "every day at 6:00 AM," "every hour," or "every Monday at 9:00 AM." n8n then runs the workflow automatically at each of those moments, forever, as long as the workflow is Active — no person needs to be present or click anything.

Where this matters — the concept of "cron": under the hood, scheduling systems (in n8n and in most software) use a format called cron to describe recurring times. You don't need to teach cron syntax in depth for this class, but it's worth naming: n8n's Schedule Trigger has a simple dropdown for common cases (every X minutes/hours/days), and an advanced "Cron Expression" option for anything unusual.

Real-world examples to give the room: "Check for new orders every 15 minutes and send a summary." "Every morning at 6 AM, pull yesterday's sales numbers and email a report." "Every Monday, check which subscriptions are expiring this week." All three are things that need to happen on a timer, regardless of whether any specific external event occurred — that's exactly what a Schedule Trigger is for.

If asked: "How is this different from a webhook?"

Say the distinction plainly: "A webhook fires because something happened somewhere else, right now, unpredictably. A schedule fires because a certain time arrived — predictable, regular, nothing external needs to happen at all."

9

Other trigger types (brief — mention, don't build)

  • App-specific triggers (e.g. a Gmail trigger, a Slack trigger) — fire when something happens inside a specific app, like a new email arriving. Under the hood these often work like a managed webhook or a scheduled check against that app.
  • Error Trigger — a special trigger that fires when another workflow fails, used to build "alert me if something breaks" automations.
  • Chat Trigger — fires when a message is sent through a chat interface, commonly used to build conversational AI assistants.

These aren't built hands-on in the masterclass, but naming them answers the natural "what else is there" question and previews the enhanced program.

10

What is JSON? (plain-English primer)

Why teach this at all: every single piece of data moving between n8n nodes is in a format called JSON. Nobody can read a node's output panel confidently without recognizing this shape, so it's worth 5 minutes even though it's "not really an n8n topic."

Definition: JSON (JavaScript Object Notation) is just a simple, structured way of writing down data as labeled pieces of information — a field name, then its value.

{
  "name": "Priya",
  "email": "priya@example.com",
  "message": "Do you take on inventory automation?"
}

Explain, pointing at each part: "This is one 'item' of data. name is a field; "Priya" is its value. Same for email and message. That's it — that's the entire idea. Every node's output is just a list of these labeled pieces of data."

11

How data flows between nodes

The single most important rule in all of n8n: a node's output becomes the next node's input. Always. No exceptions. Whatever data comes out of one box is exactly what's available to the next box in line.

Analogy: think of a relay race — each runner (node) receives the baton (the data) from the runner before them, does their leg of the race (their specific job), and passes the baton on. Nobody can hand off data they never received.

Practical consequence to teach: to use a webhook's incoming email address five nodes later, you don't need to manually copy it forward through every node — you can reach back and reference the original node directly (covered in Expressions, next).

12

The HTTP Request node

What it is: a general-purpose node that can call any web address on the internet and send or receive data from it — the "universal connector" of n8n.

Why it matters so much: n8n has hundreds of purpose-built nodes (Gmail, Slack, Google Sheets, etc.), but it's impossible for it to have a dedicated node for every service that exists. The HTTP Request node is the escape hatch: if a service has any API at all, you can talk to it with this one node, even with zero dedicated n8n support for it.

The line to say that lands this concept: "Once you understand this one node, you're no longer limited to what n8n has built — you can automate literally anything that has an API, which today is almost everything."

Key settings to know: the URL to call, the Method (GET to fetch data, POST to send data), Headers (often used to carry an authentication token), and the Body (the data being sent, for POST requests).

13

Expressions — the {{ }} syntax

What is an expression? A small piece of syntax that lets you insert a value from somewhere else in the workflow into a field, instead of typing a fixed, hard-coded value.

Why this exists: without expressions, every field you type is a fixed value — useful for testing, useless for a real automation where the data is different every single time (a different name, a different email, every run). Expressions are how a workflow stays dynamic.

The syntax, piece by piece:

{{ $json.message }}
  • {{ }} — tells n8n "don't treat this as literal text, evaluate what's inside."
  • $json — means "the data arriving at this node right now."
  • .message — the specific field you want to pull out of that data.

Field names with spaces:

{{ $json["field name"] }}

Reaching back to a specific earlier node (not just the immediately previous one):

{{ $('Webhook').item.json.email }}

Explain: "name the node you want, in quotes, inside $('...'), then walk down to the field exactly like before."

If asked: "Why does my expression show [undefined]?"

Almost always a typo or wrong capitalization in the field name. Teach the fix directly: "Click the earlier node and read its actual output panel — copy the exact field name from there instead of typing it from memory."

14

Credentials & authentication

What is a credential? A saved API key, password, or login token that a node needs in order to talk to an external service on your behalf — for example, the key that proves to an AI provider that you're allowed to use their models.

Why n8n separates credentials from nodes: if every node stored its own copy of a password, that password would be scattered everywhere and hard to change or keep safe. Instead, you create ONE credential (say, "My OpenAI Account"), and any node that needs it just selects it from a dropdown.

Analogy: think of a credential like a key card for a building — you check it out once from security, and any door that recognizes it lets you through. You don't get issued a brand new key for every single door.

Security note worth saying out loud: once a credential is saved, n8n never displays the actual key again — so a workflow can be shared, exported, or shown on screen without ever leaking the secret itself.

15

The Set / Edit Fields node

What it is: a node used to create new fields or change existing ones in the data as it flows through — reshaping data into the form a later step needs.

Why it's needed: data rarely arrives in exactly the shape you want it in for the next step. The Set node lets you add a field (e.g. combine first and last name into "full name"), rename one, or hard-code a value that should be the same on every run.

16

The IF node — conditional logic

What it is: a node that splits a workflow into two paths — "true" and "false" — based on a condition you set.

Analogy: a fork in the road with a sign: "if it's raining, go left; otherwise, go right." The IF node is that fork and that sign, built into a workflow.

Example: "If the incoming message contains the word 'urgent,' send it to one Slack channel; otherwise, send it to the normal channel." The condition ("contains urgent") decides which of the two paths the data takes next.

17

AI nodes — what an LLM is, and how the node works

What is an LLM, in one plain sentence? A large language model is an AI system trained on enormous amounts of text that can read text you give it and generate a relevant response — it predicts, very well, what a good reply looks like.

What the AI node (OpenAI / Anthropic / similar) does: it sends your text (the "prompt") to the AI provider's servers, and returns whatever text the model generates back into your workflow, as normal node output — usable by every node after it, exactly like any other data.

What a prompt is, and why it matters: the prompt is the instruction you give the model. It is the entire interface — what you write in it directly controls what comes back. Teach this explicitly with an example: telling the model "write a 3-sentence reply, and do not invent pricing or timelines" produces a reliably different (and safer) result than not saying so. The model will happily make things up if you don't tell it the boundaries.

If asked: "Is the AI 'thinking'?"

Keep this simple and honest: "It's generating text based on patterns learned from huge amounts of writing. It doesn't know facts the way a database does — it's very good at producing plausible, relevant language, which is why the instructions you give it (the prompt) matter so much."

18

Testing vs. Activating a workflow

Test workflow (the button): runs the workflow once, right now, so you can watch it happen and check the output at every node. Used constantly while building.

Active (the toggle, top-right of the editor): when turned on, the workflow starts listening for its trigger continuously and automatically — a Webhook's Production URL only works once Active is on; a Schedule Trigger only fires on its own once Active is on.

The mistake to pre-empt explicitly: "My webhook isn't working" is almost always either (a) using the Test URL instead of the Production URL for a real, live integration, or (b) forgetting to toggle Active. Teach both causes together since they're easy to confuse.
19

Executions & debugging a failed run

What is an execution? One complete run of a workflow, start to finish — every time the trigger fires (manually, by webhook, or on schedule), that's one execution, and n8n keeps a record of it.

The Executions tab: shows a history of every run, whether it succeeded or failed, and — critically for debugging — lets you click into any past run and see exactly what data was flowing through each node at that moment.

How to debug a failed workflow, as a repeatable process to teach:

  1. Open the failed execution and find the node that's marked with an error (usually shown in red).
  2. Click that node and read its input — was the data it received what you expected?
  3. If the input looks wrong, the problem is actually in an earlier node — trace backward.
  4. If the input looks right but the node still failed, check its own settings (a typo in an expression, a missing credential, a wrong field name).
