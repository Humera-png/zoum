SATURDAY

0:00 – 0:15 · OPEN

The automation mindset

Open with the test, not a definition: "Not everything should be automated. The test is two questions: is this repetitive, and is it stable — does it happen the same way every time? If both are yes, it's worth automating. If it changes shape every time, or happens once a year, automating it usually costs more effort than it saves."

Ask the room: "Give me 2–3 things you or your team do manually, the same way, regularly." Take several answers, write them on the board with how often each happens and roughly how long it takes by hand. This list becomes the seed for Sunday's capstone — say that now, so people are already thinking ahead.

Set the goal: "By 2:40 tomorrow, you will have one real automation running — something that actually replaces a task you just named, not a toy example."

0:15 – 1:00 · LIVE BUILD: AUTOMATING A REAL REPORT

The whole arc, demonstrated once before anyone touches a keyboard

Frame it: "I'm going to build, live, a script that replaces a report someone currently makes by hand every week. Watch the whole arc — the specific code matters less than seeing 'manual task' become 'script that runs in seconds.'"

import pandas as pd

df = pd.read_excel("weekly_report.xlsx")
print(df.head())                       # look at the raw data first

summary = df.groupby("region")["sales"].sum()
print(summary)

summary.to_excel("summary_output.xlsx")
print("Report generated.")

Explain each line as you go: "read_excel loads the spreadsheet exactly the way someone opens it by hand. groupby does in one line what someone currently does with pivot tables and a coffee break. to_excel writes a new file — the finished report, generated by a script instead of a person."

If asked: "What if my data isn't in Excel?"

"Pandas reads CSV, Excel, and can pull straight from a database or an API — the shape of the work is identical: load it, transform it, output it. Today we use Excel because it's the most common starting point in real offices."

1:10 – 2:10 · HANDS-ON: YOUR OWN FILE/DATA AUTOMATION

Everyone builds a version of the demo, on their own data

Provide a sample spreadsheet for anyone without one of their own. Everyone works through, with the instructor circulating rather than presenting:

  1. Load the file with pd.read_excel or pd.read_csv
  2. Look at it with .head() before doing anything else — "never transform data you haven't looked at"
  3. Produce one useful transformation — a group total, a filter, a sort
  4. Write the result to a new output file
Common mistake: trying to write output to a file that's still open in Excel on the same machine — it'll throw a permissions error. Tell the room this up front: close the source file, or always write to a differently-named output file.
Checkpoint: everyone should have a script that reads a file and writes a transformed output before moving to error handling. Walk the room and check.
2:10 – 2:50 · ERROR HANDLING & LOGGING

The difference between a script and a system you can trust

Open with the core idea, before any code: "A script that fails silently is worse than one that never existed — it gives you false confidence that something ran when it didn't. Today we make sure that never happens."

import logging

logging.basicConfig(filename="run.log", level=logging.INFO,
                     format="%(asctime)s %(levelname)s %(message)s")

try:
    result = risky_step()
    logging.info(f"Success: {result}")
except Exception as e:
    logging.error(f"Failed: {e}")
    raise

Explain each piece: "try/except means 'attempt this, and if it breaks, don't crash silently — catch it and say what happened.' logging.info writes a timestamped line to a file every time something succeeds; logging.error does the same for failures. The raise at the end re-throws the error after logging it — we want a record and we still want to know loudly that something failed."

Everyone adds this pattern around the risky step in their own Saturday script — the file read, or the transformation, whichever is more likely to break on bad input.

0:10 – 1:00 · WORKING WITH APIS

Pulling and pushing data programmatically

Frame it: "Yesterday's automation used a file that already existed. Most real automations also need to reach out to another service — check a price, look up a customer, post a message. That's an API call."

import requests

response = requests.get(
    "https://api.example.com/data",
    headers={"Authorization": "Bearer TOKEN"},
    params={"page": 1}
)
data = response.json()
print(data)

Explain line by line: "requests.get sends a request to a URL, the same way your browser does when you visit a page. The headers dictionary carries authentication — most real APIs need a token to prove who's asking. params passes extra options, like which page of results you want. .json() turns the raw response into a Python dictionary you can actually work with."

Common mistake: a 401 or 403 response means the auth header is missing or wrong — not that the URL is broken. Teach the room to check the status code first: response.status_code, before assuming the whole request failed.

Everyone pulls data from one real public API (instructor provides a free, no-signup option) and feeds it into their Saturday pipeline as a second data source — the shape almost every real business automation takes: a file, plus an API, combined.

1:10 – 1:40 · SCHEDULING

The difference between a script you remember to run and one that just runs

from apscheduler.schedulers.blocking import BlockingScheduler

def my_automation():
    print("Running the automation...")
    # the Saturday + API logic goes here

scheduler = BlockingScheduler()
scheduler.add_job(my_automation, 'cron', hour=6, minute=0)
scheduler.start()

Explain: "This wraps everything built so far into a function, then tells APScheduler to call that function every day at 6am, forever, without anyone starting it by hand. This one block is what turns a script into a system." Mention cron as the equivalent for anyone running on a Linux server rather than a local Python process — same idea, different tool.

1:40 – 2:40 · USING AI TO AUTOMATE A DECISION

Build your capstone — the AI's output becomes an automated action

Frame the shift explicitly: "Everything so far moves and transforms data. This step makes a decision — using AI to decide what happens next, automatically, not just report a number for a person to act on."

response = ai_client.messages.create(
    model="claude-...",
    max_tokens=50,
    messages=[{
        "role": "user",
        "content": f"Classify this record as urgent, normal, or low. Reply with one word only.\n\nRecord: {record}"
    }]
)
category = response.content.strip().lower()

if category == "urgent":
    send_alert(record)
else:
    log_normally(record)

Explain the key idea: "The AI's answer — 'urgent,' 'normal,' or 'low' — becomes a Python if condition. The automation now branches based on what the AI decided, without a person reading anything first. That's the whole difference between 'AI that reports' and 'AI that acts.'"

Build the capstone now: each attendee adds one AI-driven decision point to their own Saturday+Sunday pipeline — instructor circulates to help finish a genuinely working automation for as many people as possible before time runs out.
